# 如何在自己的应用代码中跟踪并暴露指标

> 本篇是一个**完整实操**：我从零写了一个演示的应用 `prom-demo`（django-ninja），给它埋点、打成镜像、部署到 K8s、让[Kubernetes 集群监控体系——Prometheus+Grafana+Alertmanager ](https://blog.fz688.dpdns.org/2026/07/20/安装并使用-Prometheus：kube-prometheus-stack/)装好的 Prometheus **自动发现并抓取它**，最后在 Prometheus 里查到自己的业务指标。全部代码在 [FZ688/prom-demo](https://github.com/FZ688/prom-demo)仓库里。

---

## 四种指标类型

[01-Prometheus 基础知识](https://blog.fz688.dpdns.org/2026/07/19/Prometheus-基础知识/)讲过概念：


| 类型          | 定义                     | 值的规律                    | 典型例子                     | 演示应用里的对应实现          |
| ------------- | ------------------------ | --------------------------- | ---------------------------- | ----------------------------- |
| **Counter**   | 只增不减的计数器         | 重启归零，靠`rate()` 看速度 | 订单数、请求数、错误数       | `demo_orders_total`           |
| **Gauge**     | 可增可减的瞬时值         | 看瞬时值本身                | 在线人数、队列长度、内存占用 | `demo_active_users`           |
| **Histogram** | 客户端分桶、服务端算分位 | 桶是累计计数器              | 请求耗时、订单金额分布       | `demo_order_duration_seconds` |
| **Summary**   | 客户端流式算分位         | 无法跨实例聚合              | 单实例 SLA 精确分位          | -                             |

**选型**：数数量用 Counter，看状态用 Gauge，要查看"多快/多大"用 Histogram，Summary 几乎不用。

## 创建项目： Django + ninja 应用

目标是让每行代码都能讲清楚，所以项目刻意保持极小：

```
prom-demo/
├── manage.py          
├── requirements.txt   
├── Dockerfile         
├── deploy-k8s.yaml      # Deployment + Service + ServiceMonitor
└── demo/
    ├── settings.py    
    ├── urls.py          # 将 /metrics 端点暴露
    ├── metrics.py       # 自定义业务指标定义
    ├── api/
    │   ├── views.py     # 业务接口
    │   └── urls.py    
    ├── apps.py
    └── wsgi.py
```

依赖三件套（`requirements.txt`）：

```text
django>=5.0,<5.3
django-ninja>=1.3
django-prometheus>=2.3.1
gunicorn>=23.0
```

> **django-prometheus 是什么？** 一个把 Django 和 `prometheus_client`（Prometheus 官方 Python 客户端库）集成起来的库。主要功能是：暴露 `/metrics` 端点、自动采集 Django 框架指标（HTTP 请求计数/耗时、迁移状态）、并把我们写的自定义指标一并挂到同一个端点上。

## 应用埋点

### 注册 app + 中间件（settings.py）

```python
INSTALLED_APPS = [
    "django.contrib.staticfiles",
    "django_prometheus",   #  加这一行
    "ninja",
    "demo",
]

MIDDLEWARE = [
    # 顺序有要求：Before 放最前、After 放最后
    "django_prometheus.middleware.PrometheusBeforeMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django_prometheus.middleware.PrometheusAfterMiddleware",
]
```

![image-20261008215159636](https://img.fz688.dpdns.org/2026-10-08-1791467520578.png)

**为什么中间件顺序是必须是Before 放最前、After 放最后？** Before 中间件在请求进入 Django 前就记下开始时间，After 中间件在响应走完全部流程后完结计时。如果放反了（比如 After 在最前），视图和后续中间件的耗时就被排除在观测之外，直方图会系统性偏小。

另外配置：

![image-20261008215257124](https://img.fz688.dpdns.org/2026-10-08-1791467577407.png)

```python
# 关闭迁移导出（demo 不需要 django_migrations_* 指标）
PROMETHEUS_EXPORT_MIGRATIONS = False
```

![image-20261008215357600](https://img.fz688.dpdns.org/2026-10-08-1791467638020.png)

一个 /metrics 里已经拿到三类指标：**Django 框架**（每个视图的请求数）、**Python 运行时**（GC、线程）、**进程**（内存、CPU、打开的文件句柄）。想看这几个基础指标，之后再谈谈业务指标，大多数性能问题首先要看的就在进程指标里。

### 定义业务指标（metrics.py）

```python
from prometheus_client import Counter, Gauge, Histogram

ORDERS_TOTAL = Counter(
    "demo_orders_total",
    "Total number of orders created",
    labelnames=("type",),
)

ACTIVE_USERS = Gauge(
    "demo_active_users",
    "Current number of simulated active users",
)

ORDER_DURATION = Histogram(
    "demo_order_duration_seconds",
    "Order creation duration in seconds",
    buckets=(0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.0, 3.0),
)
```

![image-20261008215651147](https://img.fz688.dpdns.org/2026-10-08-1791467811572.png)

**三个比较容易踩的坑**：

1. **指标名是"写进数据库"的**。Prometheus 的 TSDB 不会修改历史——也就是说我今天命名成 `demo_orders_total`，明天改名 `demo_order_count_total`，旧的序列会永远留在存储里直到过期。所以上线前需要想好命名（惯例是：`<项目>_<域>_<对象>_<单位>`）。
2. **`_created` 是什么？** 暴露端点里你会看到 `demo_orders_created{type="vip"} 1.7898e+09`——这是 Python client 2.x 起为 OpenMetrics/原生直方图准备的"创建时间戳"伴生指标，普通用途忽略它即可。
3. **Histogram 的桶是"累计上界"**。`le="0.05"` 的桶值是"耗时 ≤50ms 的请求数"，不是"耗时在 25~50ms 的请求数"。所以算"50ms 内的占比"直接用两个桶相除，算"25~50ms 区间"要相邻桶相减（[03-PromQL 查询语言入门与实战 ](https://blog.fz688.dpdns.org/2026/07/20/PromQL-查询语言入门与实战/)的 `histogram_quantile` 就是这么算的）。

### 在业务代码里记数（views.py）

```python
@router.post("/order")
def create_order(request, type: str = "normal"):
    with ORDER_DURATION.time():            
        time.sleep(random.uniform(0.005, 0.08))
        ORDERS_TOTAL.labels(type=type).inc() # Counter：按 type 维度 +1
    return {"ok": True, "type": type}
```

埋点——**一个 `with`，一个 `.inc()`**。需要注意：

- **`labels()` 的调用开销极小**（本质是字典查找），热路径可以放心埋点；
- **不要在循环里 `labels()` 拼接无限值**（比如把订单号塞进 label），要聚合维度（比如这个项目里的type），不要使用实体 ID。

Gauge 的用法：

```python
@router.get("/stats")
def stats(request, delta: int = 1):
    ACTIVE_USERS.inc(random.randint(0, 10) * delta) 
    return {"active_users": ACTIVE_USERS._value.get()}
```

## 打包成镜像：

`Dockerfile` ：

```dockerfile
FROM docker.io/library/python:3.13-slim
# FROM docker.m.daocloud.io/library/python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt

COPY . .

# 容器启动时自动建库（简化操作，生产应该用 init job 或迁移镜像）
RUN python manage.py migrate --noinput

EXPOSE 8000

#  1 worker + 4 threads，解决指标聚合问题
CMD ["gunicorn", "demo.wsgi:application", \
     "--bind", "0.0.0.0:8000", \
     "--workers", "1", "--threads", "4"]

```

![image-20261008221349089](https://img.fz688.dpdns.org/2026-10-08-1791468829435.png)

**踩过的坑：多 worker 与指标聚合**。我最初写的启动命令是 `--workers 2 --worker-class prometheus_client.gunicorn.PrometheusWorker`（老教程的写法，让 gunicorn master 聚合各 worker 的指标），容器直接崩：

```text
ModuleNotFoundError: No module named 'prometheus_client.gunicorn'
```

**根因**：新版 `prometheus_client` 已经**移除**了 gunicorn worker 集成。其实是因为——**每个 gunicorn worker 是独立进程，各自持有独立的一套 counter**。不聚合的话，`/metrics` 的值取决于这次请求恰好打到哪个 worker，数字会来回跳。

**三种解法**：


| 方案                           | 原理                                                                                               | 代价                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------- | -------------------------- |
| 旧：PrometheusWorker（已移除） | master 进程聚合各 worker                                                                           | 已被淘汰                   |
| 新：multiprocess 模式          | 各 worker 把指标写共享目录（`PROMETHEUS_MULTIPROC_DIR`），/metrics 里合并                          | 要挂载共享卷、历史清理麻烦 |
| **K8s 云原生方案（本次采用）** | 单 worker 多线程（线程共享内存，指标天然一致）+**Pod 副本横向扩展**，Prometheus 对每个副本分别抓取 | 零额外设施                 |

**这也是云原生对可观测性的好处**：把"进程内多 worker 聚合"这个问题，消解成"每副本一个可抓取的端点"。K8s 场景下，扩容 相当于 增加被 Prometheus 自动发现的新目标，指标体系天然水平伸缩。

## 上 K8s + 让 Prometheus 自动发现（ServiceMonitor）

部署清单（`deploy-k8s.yaml`，完整文件见 [FZ688/prom-demo](https://github.com/FZ688/prom-demo)，三件套：**Deployment（2 副本）+ Service（NodePort 30810）+ ServiceMonitor**。

前两个是普通 Django 应用的标准做法，这篇文章最重要的时是后面这个 **ServiceMonitor** ：

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: prom-demo
  namespace: prom-demo
spec:
  selector:                  # 匹配带 app=prom-demo 标签的 Service
    matchLabels:
      app: prom-demo
  namespaceSelector:         # Service 所在的 ns
    matchNames:
      - prom-demo
  endpoints:              
    - port: http             # 引用 Service ports[].name
      path: /metrics
      interval: 15s       
```

**无需重启、无需改 Prometheus 任何配置**，apply 完等一轮抓取间隔，[02-Kubernetes 集群监控体系——Prometheus+Grafana+Alertmanager | FZ's Blog](https://blog.fz688.dpdns.org/2026/07/20/安装并使用-Prometheus：kube-prometheus-stack/)部署的 Operator 就自动把新目标纳入监控。打开 Prometheus 的 `/targets` 页搜索 prom-demo：

![targets 页：prom-demo 的两个副本目标全部 UP](https://img.fz688.dpdns.org/2026-10-08-1791470341120.png)

**读图**：`serviceMonitor/prom-demo/prom-demo/0` 分组下出现 **2/2 up**——两个 Pod 副本（`10.1.1.45:8000`、`10.1.1.46:8000`）各自成为一个独立抓取目标，`job="prom-demo"`、`namespace="prom-demo"` 标签自动附加。至于为什么 ServiceMonitor 一创建就生效？与namespace 选择器的配置逻辑（`serviceMonitorSelectorNilUsesHelmValues: false`）和 Operator 的翻译流水线，后面再讲解。

然后打真实流量，去 Prometheus 查自己的业务指标：

```bash
# 给 demo 造 90 秒订单流量（POST 触发 Counter）
$ for i in $(seq 1 22); do
    curl -X POST "http://localhost:30810/api/order?type=vip" > /dev/null
    [ $((i % 3)) -eq 0 ] && curl -X POST "http://localhost:30810/api/order?type=normal" > /dev/null
    sleep 3
  done
```

查询 `sum by (type) (demo_orders_total)`（Graph 视图）：

![业务指标曲线：两条订单类型的 Counter 阶梯上升](https://img.fz688.dpdns.org/2026-10-08-1791470445298.png)

**读图**：两条阶梯上升的曲线——`type="vip"`（到 27）和 `type="normal"`（到 12）。Counter 的形态就是这样**单调不减、只涨不跌**；两条曲线的斜率之差，就是"VIP 订单比普通订单多"这个场景的数学表达。Table 视图同查询的输出：

```text
{type="normal"}   12
{type="vip"}      27
Result series: 2
```

Histogram 也已经工作了（`/metrics` 输出，累计桶）：

```text
demo_order_duration_seconds_bucket{le="0.005"}  0.0
demo_order_duration_seconds_bucket{le="0.01"}   1.0
demo_order_duration_seconds_bucket{le="0.025"}  4.0
demo_order_duration_seconds_bucket{le="0.05"}   13.0
demo_order_duration_seconds_bucket{le="0.1"}    21.0
demo_order_duration_seconds_bucket{le="0.25"}   21.0
demo_order_duration_seconds_bucket{le="0.5"}    21.0
```

**读输出**：21 单订单里，≤10ms 的 1 单、≤25ms 的 4 单、≤50ms 的 13 单、≤100ms 的 21 单——0.1s 之后不再增长说明没有超过 100ms 的订单（桶设计合理）。用 [03-PromQL 查询语言入门与实战 | FZ's Blog](https://blog.fz688.dpdns.org/2026/07/20/PromQL-查询语言入门与实战/) 的 PromQL 算 P95：

```promql
histogram_quantile(0.95, sum by (le) (rate(demo_order_duration_seconds_bucket[5m])))
```

## 改不了代码的系统怎么办

本篇的前提是代码是我们自己编写的。但 MySQL、Redis、Linux 主机、Nginx、你司十年前的祖传系统，都改不了代码。让它们也能被 Prometheus 抓，靠的是 **Exporter**，之后会详细讲讲Exporter.
